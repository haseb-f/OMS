## 1. Customer direction — traced lifecycle

Invoice (posted: Dr AR partner / Cr revenue) → receipt `CUSTOMER_RECEIPT` → allocation rows → Confirm → Posting Engine
(`financial-transaction-posting.provider.ts:187-266`: Dr `ReceivingAccount.chartOfAccountId` (or a declared claim's clearing
`debitAccountId`) / Cr AR (partner) [+ Dr fee account, ± realized FX]) → JE `sourceType=CUSTOMER_RECEIPT, sourceId=<voucher>` →
partner statement (`accounting-reports.service.ts:1382`, JE lines on RECEIVABLE accounts) → aging (`:1444`, documents + allocations)
→ invoice status (`shared/invoice-payment.util.ts:56` `computeInvoicePaymentSummary`, CONFIRMED allocations only).

Proven by `trace — customer 200,000 / 100,000 …` (real Posting Engine): draft has **no** JE and pays nothing; confirm →
PARTIALLY_PAID, remaining 100,000 on detail / open invoices / aging; **one** JE linked to the voucher; bank +100,000 (not 200,000);
AR statement 100,000. Second installment 130,000 (100,000 applied) → PAID, bank 230,000, AR −30,000, aging unapplied 30,000 /
net −30,000, position received 230,000 / applied 200,000 / unapplied 30,000. `trace — one receipt over several invoices, cancel …`:
150,000 over two invoices, cancel = one POSTED + one REVERSED entry, bank 0, both invoices UNPAID, second cancel refused.
`trace — two posted advances racing …`: exactly one allocation lands (invoice row lock `invoice-payment.util.ts:134`).
Store-order collections use the same service (`store-order-collection.service.ts:225` create, `:355` allocate advances).

## 2. Supplier direction — traced lifecycle

Purchase invoice (Cr AP partner) → `SUPPLIER_PAYMENT` → Confirm → Dr AP (partner) / Cr bank ± FX (`posting.provider.ts:277-322`)
→ JE linked → AP statement → AP aging → status. `trace — supplier 200,000 / 100,000 …`: PARTIALLY_PAID 100,000 everywhere,
bank −100,000, AP 100,000; a 40,000 advance (AP 60,000) later allocated → paid 140,000, still **one** entry, bank −140,000.

## 6. Repair plan (order; reuse the one FT service + Posting Engine — no second workflow)

1. **Settlement summary (S1, S2)** — extend `computeInvoicePaymentSummary` with `creditedTotal` (posted returns against the invoice,
   applied up to the open balance; surplus stays refundable credit) and a `sumPostedCredits()` beside `sumConfirmedAllocations`; use it
   in every consumer (invoice list / detail / export, open invoices, `assertAllocationWithinRemaining`, aging, store-order
   `openInvoices`, cash-flow candidates); aging `unappliedCredits` subtracts the applied part. Status for a credit-settled invoice: OQ-2.
2. **Aging per currency (A1, A3)** — key partner rows by partner + currency, invoice rows carry the currency, `totalsByCurrency`
   (unapplied in the voucher's currency); as-of uses `allocation.allocationDate`. Web aging renders per-currency totals (I-B).
3. **Allocation guards (L1, L2, L3, L5, V1)** — in `resolveAllocations` / `allocate`: remaining-balance check at entry, company match,
   refuse agent-collection receipts (and exclude them from position / aging unapplied), re-read status after the row lock; fee ≤ amount
   in `create` + `setActualFee` + bank DTO (cap rule OQ-5).
4. **Atomic operations (W1, L4)** — `PATCH financial-transactions/{receipts|payments}/:id/allocations/:allocationId`
   (`updateAllocation`: one tx, voucher + invoice locks, existing guards); both editors use it and reload on failure. Bank-line confirms
   use `createConfirmed` with an idempotency key from the bank line id.
5. **Posting (P1, P2, P4, P3)** — settlement FX through the Posting Engine: a provider for allocation adjustments (e.g. sourceType
   `FT_ALLOCATION_FX`, sourceId = allocation id) posting Dr/Cr AR|AP partner vs realized FX when the invoice rate ≠ voucher rate;
   unallocate reverses it (engine `reverse`) and, for a Confirm-time allocation, posts the counter-adjustment; the settling allocation
   clears the invoice's remaining carrying amount (P4). Entry date = voucher date once OQ-1 is answered (transfers: outgoing leg date).
6. **Archive rule (A2)** — refuse archiving a posted invoice with an open balance (or any posted invoice, OQ-3).
7. **Integrity endpoint** — add: partner AR/AP vs aging net per currency (FX / rounding residue), agent receipts allocated to invoices,
   allocations on cancelled vouchers, drafts over-claiming invoices.
8. **Data (§6)** — no posted entry to change. After the code: re-run probe + R20 audit (before/after). With owner approval only,
   `r20-repair-payment-status.mjs --apply --allocate CR-2026-000103=INV-2026-000093` (allocate, no cash entry, idempotent).
9. **§2 gaps** — only after the owner answers OQ-4: new `FinancialTransactionType`s on the same service / provider (other receipt /
   other payment with an authorized counter-account list in Settings, receipt-advance refund, supplier refund, manual internal
   transfer reusing the transfer posting) — not new modules.
