## Verified correct (evidence)

- **Postings** — receipt: Dr receiving account's ledger (or a declared claim's method clearing `debitAccountId`) / Cr partner AR
  (`resolveReceivableAccount`, partnerId on the line) + fee line + realized FX on the exchange-difference account; supplier
  payment mirrored on partner AP; `FT_ALLOCATION_FX` = partner control account (the one the voucher's entry used) vs exchange
  difference, journal GENERAL, `sourceId` = voucher. Every entry of the VERIFY vouchers is balanced (`assertBalanced`). Drafts
  never post (R22 trace); Confirm is row-locked + status re-read: two concurrent confirms → one entry (VERIFY); cancel reverses
  the voucher entry **and** its FX adjustment exactly once, a second cancel is refused (VERIFY, D6 test).
- **FX matrix** (VERIFY): invoices @10 / @11, receipts @12 / @9 / @12 — confirm-time allocation, later allocate, PATCH down
  (invoice re-opens), reallocation to a second invoice, overpayment, cancel of one instalment: after every step partner AR =
  Σ open × invoice rate − Σ unapplied × voucher rate **exactly**, each voucher's FX = cash − cleared, ≤ 1 active adjustment
  per voucher. Functional-currency vouchers never create an `FT_ALLOCATION_FX` entry (VERIFY). P4 rounding: residue ≤ 0.05
  absorbed into FX, never AR (R22 P4 test).
- **D2** — one summary (`loadInvoiceSettlements`) used by list / detail / open invoices / capacity guards / aging / store-order
  `openInvoices` / cash-flow candidates; `paidTotal` (= `allocatedTotal`) is cash only; credit = min(unrefunded, total − paid);
  surplus listed as unapplied credit; a SETTLED invoice refuses another allocation (`ALLOCATION_EXCEEDS_INVOICE_BALANCE`) —
  except via F2 / F4. Store-order money position is order-level (expected = invoiced − credited) and agrees with the
  invoice summaries in aggregate. No "reverse return" operation exists (archive is the only path — F2).
- **Aging per currency** (A1 tests): rows per partner × currency, `totalsByCurrency`, `totals` = functional only; functional
  aging net = ledger for open / settled / surplus cases (D2 test) — except F3 / F5 / F6.
- **Migration** — additive (only `allocation_date` + 2 `IF NOT EXISTS` indexes), touches no entry / amount / status; on the
  template data every moved line lands on its entry's day (F9 caveats only).
- **Boundaries** — agent collection never allocates / never counts as customer credit (L2), other company refused (L5),
  currency fixed at allocate / confirm, counterparty checked in `resolveAllocations`; settlement history = invoice `view`,
  actions from voucher `edit` / `cancel` (allocation numbers are already on the invoice detail — no new disclosure).
- **P3 / periods** — entry date = voucher date (P3 test); back-dated Confirm into a closed period refused, nothing posted
  (D1 test + VERIFY); a voucher posted in a period that is later closed keeps its entry there, its later allocation FX and
  its cancel reversal post today (VERIFY).
- **Concurrency** — PATCH vs Allocate racing for the last balance: exactly one lands; two Allocates on one foreign voucher:
  both land, one active FX entry, FX −300 exact (VERIFY); allocate vs cancel re-read under lock (L1); bank-line vouchers
  `createConfirmed` with `bank-line:<id>:<updatedAt>` (replay returns the same voucher; payload compared).

voucher entry's day. Data steps re-run on the migrated, used `oms_r22_review`: `UPDATE 0`, `INSERT 0` (idempotent).

lines (earlier unallocations / cancels are not reconstructed). T: three enum values, nullable columns with
`ON DELETE SET NULL` FKs, number series `ON CONFLICT DO NOTHING` — additive, idempotent.
